# 校园通知屏系统 PRD

## 1. 文档信息

- 项目名称：校园通知屏系统
- 文档类型：PRD + 一期技术设计基线
- 创建日期：2026-04-21
- 当前版本：V1.0
- 适用范围：微信小程序、FastAPI 后端、Windows 桌面端

## 2. 项目背景

目标是搭建一套轻量、实时、可常驻运行的通知系统，支持微信小程序用户向指定 Windows 桌面端发送显眼通知。桌面端设备通常为开机自启、长期在线状态，用于教室、办公室、值班室、门卫室、机房或公告屏场景。

系统需满足以下核心诉求：

1. 用户通过微信小程序即可绑定一台或多台 Windows 设备。
2. 多个用户可以绑定同一台 Windows 设备，且绑定后均可发送通知。
3. Windows 桌面端随系统启动自动运行，保持常驻并实时接收通知。
4. 通知要足够醒目，不能只依赖普通系统弹窗。
5. 通知需要支持滚动展示、短卡片提醒、语音播报、展示时长自定义。
6. 小程序上必须实时显示设备在线状态，离线设备不可发送。

## 3. 产品目标

### 3.1 业务目标

1. 提供一套低学习成本的跨端通知方案。
2. 将通知发送门槛降低到微信小程序内即可完成。
3. 保证设备在线时通知可秒级到达并醒目展示。
4. 支持一个设备被多个用户共享使用。

### 3.2 一期目标

1. 完成小程序登录、设备绑定、设备在线状态展示。
2. 完成单台和多台设备发送通知。
3. 完成 Windows 桌面端常驻、自启动、横幅展示、卡片提醒、语音播报。
4. 完成后端通知推送、送达回执、发送记录查询。

### 3.3 非目标

一期暂不包含以下内容：

1. 设备分组。
2. 全体广播。
3. 富文本、图片、视频通知。
4. 复杂权限体系。
5. 离线补发。
6. Web 管理后台。

## 4. 用户角色

### 4.1 小程序用户

具备微信身份，能够绑定设备、查看设备状态、发送通知、查看发送记录。

### 4.2 Windows 设备

安装桌面客户端的电脑，拥有唯一设备身份，开机自启并保持长连接。

### 4.3 系统后端

负责登录鉴权、设备管理、绑定关系、通知下发、在线状态、消息回执与记录存储。

## 5. 产品范围

### 5.1 微信小程序

一期包含以下能力：

1. 微信登录。
2. 设备列表。
3. 设备在线状态显示。
4. 扫码绑定设备。
5. 手动输入绑定码绑定设备。
6. 单台或多台设备发送通知。
7. 发送记录查询。

### 5.2 Windows 桌面端

一期包含以下能力：

1. 安装后生成唯一设备标识。
2. 开机自启。
3. 后台常驻与系统托盘。
4. 显示当前绑定码和二维码。
5. 长连接保持在线。
6. 通知短卡片提醒。
7. 顶部滚动横幅展示。
8. 语音播报。
9. 紧急通知高亮、重复播报、手动关闭。

### 5.3 后端服务

一期包含以下能力：

1. 微信小程序登录。
2. JWT 鉴权。
3. 设备注册。
4. 绑定码生成与校验。
5. 绑定关系管理。
6. 在线状态维护。
7. 通知创建与实时推送。
8. 通知回执存储。
9. 发送记录查询。

## 6. 已确认产品规则

以下规则已在需求讨论中确认，作为一期固定基线：

1. 系统由三个服务组成：微信小程序、FastAPI 后端、Windows 桌面端。
2. 一个 Windows 设备可以被多个用户绑定。
3. 多个绑定用户之间不区分权限，绑定后都可以发通知。
4. 设备绑定方式支持两种：扫码绑定、手动输入绑定码。
5. 发送范围支持：单台设备、多台设备。
6. 一期不支持设备组和全量广播。
7. 通知内容结构为：标题、正文、紧急级别。
8. 展示方式为：滚动横幅为主，短卡片提醒为辅。
9. 通知展示时长支持自定义，建议预设：10 秒、30 秒、60 秒、常驻。
10. 小程序必须显示设备在线状态。
11. 只有在线设备允许发送。
12. 离线设备不可发送，且一期不做离线补发。
13. 桌面端为常驻运行设备，需支持开机自启。

## 7. 核心使用场景

### 7.1 场景一：绑定一台值班电脑

1. 值班电脑安装 Windows 客户端。
2. 客户端启动后显示绑定码和二维码。
3. 小程序用户扫码或输入绑定码完成绑定。
4. 绑定成功后，小程序设备列表出现该设备。

### 7.2 场景二：向单台设备发送通知

1. 用户打开小程序。
2. 进入设备列表，选择一台在线设备。
3. 输入标题、正文、紧急级别、展示时长。
4. 提交后由后端实时推送至对应 Windows 端。
5. Windows 端先显示短卡片，再进入顶部滚动横幅，并按规则语音播报。

### 7.3 场景三：向多台设备同时发送通知

1. 用户在设备列表勾选多台在线设备。
2. 填写通知内容并发送。
3. 后端为每台设备生成单独投递记录。
4. 各设备独立接收、展示、播报并回传状态。

### 7.4 场景四：设备离线

1. 小程序列表显示设备为离线。
2. 离线设备置灰且不可勾选。
3. 若发送瞬间设备刚离线，后端返回错误：设备已离线，请稍后重试。

## 8. 功能需求

### 8.1 小程序功能需求

#### 8.1.1 登录

1. 用户首次进入小程序时进行微信登录。
2. 后端根据微信身份创建或更新用户。
3. 返回 JWT 用于后续接口访问。

#### 8.1.2 设备列表

1. 展示当前用户已绑定设备列表。
2. 字段包含：设备名称、设备编号、在线状态、最后在线时间。
3. 在线设备优先排序。
4. 离线设备置灰显示。

#### 8.1.3 绑定设备

1. 支持扫码绑定。
2. 支持手动输入绑定码绑定。
3. 绑定码需设置时效，建议 5 分钟。
4. 一个设备可以被多个用户绑定。

#### 8.1.4 发送通知

1. 支持选择单台或多台设备。
2. 仅允许勾选在线设备。
3. 通知字段包括：标题、正文、紧急级别、展示时长、是否语音播报。
4. 发送前需校验用户与设备之间存在绑定关系。
5. 发送成功后展示每台设备的投递状态。

#### 8.1.5 发送记录

1. 支持查看最近发送记录。
2. 记录展示：标题、目标设备数、创建时间、投递结果。
3. 支持查看每台设备的送达状态明细。

### 8.2 Windows 客户端功能需求

#### 8.2.1 设备身份

1. 首次启动生成唯一 `device_id`。
2. 本地存储设备配置与设备名称。
3. 启动后向后端注册当前设备。

#### 8.2.2 自启动与常驻

1. 支持开机自启。
2. 支持系统托盘常驻。
3. 关闭主窗口不退出进程，仅收起到托盘。

#### 8.2.3 绑定展示

1. 主界面展示当前设备名称。
2. 显示短期有效绑定码。
3. 将绑定码渲染成二维码供小程序扫码。

#### 8.2.4 在线与心跳

1. 启动后建立 WebSocket 长连接。
2. 定时向后端发送心跳。
3. 连接断开时自动重连。

#### 8.2.5 通知展示

1. 新通知到达时先弹出短卡片提醒。
2. 随后将消息加入顶部滚动横幅区域。
3. 横幅需支持高亮色、字号调整和滚动效果。
4. 支持按发送配置控制展示时长。
5. 支持常驻消息，直到手动关闭或被替换。

#### 8.2.6 语音播报

1. 支持系统 TTS。
2. 普通通知默认播报 1 次。
3. 紧急通知支持重复播报，建议 3 次。
4. 紧急通知支持手动关闭。

### 8.3 后端功能需求

#### 8.3.1 鉴权

1. 提供微信登录接口。
2. 对小程序接口使用 JWT 鉴权。
3. 对 Windows 设备连接使用设备身份校验。

#### 8.3.2 绑定管理

1. 生成短期绑定码。
2. 校验扫码或手动输入绑定。
3. 保存用户与设备的多对多绑定关系。

#### 8.3.3 在线状态

1. 管理设备 WebSocket 连接。
2. 维护设备在线状态和最后在线时间。
3. 对外提供设备状态查询接口。

#### 8.3.4 通知下发

1. 创建通知主记录。
2. 为每个目标设备生成投递记录。
3. 仅向在线设备投递。
4. 推送失败时返回明确失败原因。

#### 8.3.5 回执管理

1. 记录设备是否已接收。
2. 记录设备是否已展示。
3. 记录设备是否已播报。
4. 保存错误信息和时间戳。

## 9. 非功能需求

### 9.1 性能

1. 在线设备接收通知目标时延为秒级。
2. 单条通知可同时投递给多台设备。
3. 小程序设备列表查询响应时间目标小于 1 秒。

### 9.2 可用性

1. Windows 客户端需具备自动重连能力。
2. 后端异常时不得导致客户端崩溃。
3. 长时间运行不得出现明显内存泄漏。

### 9.3 安全性

1. 绑定码短期有效并不可复用过久。
2. 用户仅可操作自己已绑定设备。
3. 所有接口必须进行鉴权。
4. 设备连接建议使用签名或令牌校验。

### 9.4 可维护性

1. 后端采用清晰模块划分。
2. 日志需覆盖登录、绑定、推送、回执和异常。
3. 核心业务表需保留创建时间、更新时间、状态字段。

## 10. 通知规则设计

### 10.1 紧急级别

一期定义三级：

1. `normal` 普通
2. `important` 重要
3. `urgent` 紧急

### 10.2 展示策略

#### 普通通知

1. 默认颜色：蓝色或品牌主色。
2. 短卡片停留较短。
3. 横幅按用户设置时长滚动。
4. 语音默认播报 1 次。

#### 重要通知

1. 默认颜色：橙色。
2. 字号略大于普通通知。
3. 卡片停留更久。
4. 横幅展示时长建议不低于 30 秒。

#### 紧急通知

1. 默认颜色：红色高亮。
2. 字号更大。
3. 优先进入横幅队列前列。
4. 支持重复播报，建议 3 次。
5. 支持手动关闭。
6. 支持常驻。

### 10.3 展示时长

建议后端使用枚举或秒数，前端预设以下选项：

1. 10 秒
2. 30 秒
3. 60 秒
4. 常驻

## 11. 在线状态设计

### 11.1 状态定义

1. `online` 在线
2. `offline` 离线

### 11.2 判定规则

1. Windows 端建立 WebSocket 后可标记为在线。
2. 客户端每 30 秒发送一次心跳。
3. 后端超过 90 秒未收到心跳则判定离线。
4. 后端记录 `last_seen_at` 作为最后在线时间。

### 11.3 小程序展示规则

1. 在线设备可选。
2. 离线设备不可选。
3. 列表按在线优先排序。
4. 设备详情显示最后在线时间。

## 12. 绑定流程设计

### 12.1 扫码绑定流程

1. Windows 端启动后向后端申请绑定码。
2. 后端生成短期有效 `bind_code`，并可编码为二维码内容。
3. Windows 端展示二维码。
4. 小程序扫码后提交绑定请求。
5. 后端校验绑定码有效性并建立用户与设备的绑定关系。
6. 返回绑定成功结果。

### 12.2 手动绑定流程

1. Windows 端展示绑定码。
2. 小程序用户输入绑定码。
3. 后端校验绑定码并完成绑定。

### 12.3 绑定码规则

1. 建议长度 6 到 8 位。
2. 建议有效期 5 分钟。
3. 可重复申请刷新。
4. 实际存储放入 Redis。

## 13. 通知流程设计

### 13.1 发送流程

1. 小程序用户选择一个或多个在线设备。
2. 填写标题、正文、紧急级别、展示时长和播报配置。
3. 小程序调用后端发送接口。
4. 后端校验 JWT、绑定关系、设备在线状态。
5. 后端创建通知主记录。
6. 后端为每个目标设备创建投递记录。
7. 后端通过 WebSocket 推送到在线设备。
8. Windows 端收到后返回接收回执。
9. Windows 端展示完成后回传展示回执。
10. 若开启播报，完成后回传播报回执。

### 13.2 异常流程

1. 若设备离线，发送失败并返回错误。
2. 若部分设备离线，多发场景下返回部分成功结果。
3. 若 Windows 端收到后展示失败，需回传失败原因。

## 16. 技术架构设计

### 16.1 总体架构

采用三端架构：

1. 微信小程序作为用户操作入口。
2. FastAPI 单体服务同时承担 HTTP API 和 WebSocket 网关职责。
3. Windows WPF 客户端作为设备侧常驻应用。

### 16.2 技术栈建议

#### 小程序

1. 微信原生小程序。
2. 使用微信登录能力。

#### 后端

1. FastAPI
2. SQLAlchemy 2.x
3. Pydantic
4. MySQL
5. Redis
6. Uvicorn
7. JWT

#### Windows 端

1. .NET 8
2. WPF
3. 系统托盘
4. Windows TTS
5. WebSocket 客户端

### 16.3 后端模块建议

1. `auth`：微信登录、JWT。
2. `device`：设备注册、在线状态、心跳。
3. `binding`：绑定码生成、扫码绑定、手动绑定。
4. `notification`：通知创建、查询。
5. `delivery`：投递明细与回执。
6. `ws_gateway`：维护设备长连接与消息推送。

### 16.4 Redis 使用建议

1. 存储绑定码和有效期。
2. 存储设备在线状态缓存。
3. 存储设备连接索引。

## 18. Windows 展示设计

### 18.1 展示原则

1. 以横幅为主，而非纯系统弹窗。
2. 先提醒，再持续展示。
3. 通知必须足够醒目但不影响设备稳定性。

### 18.2 具体行为

1. 新通知到达时显示短卡片提醒。
2. 卡片展示后自动收起。
3. 同时将消息加入顶部滚动横幅。
4. 横幅滚动结束后按规则消失。
5. 常驻消息需保留，直到手动关闭。

### 18.3 后续增强方向

1. 支持顶部/底部位置切换。
2. 支持字体大小配置。
3. 支持滚动速度配置。
4. 支持多屏幕显示策略。

## 19. 安全与风控建议

1. 绑定码必须短时有效。
2. 设备注册时应下发设备令牌。
3. WebSocket 建立时应校验设备令牌。
4. 所有用户操作记录操作人、目标设备、时间。
5. 对通知内容可增加长度限制与敏感词策略。

## 20. 日志与监控建议

### 20.1 后端日志

4. 通知创建、推送、回执。

## 22. 风险与注意事项

1. Windows 长期常驻运行要重点验证内存和句柄泄漏。
2. WebSocket 重连需要处理重复连接和旧连接清理。
3. 多设备同时发送时要考虑部分成功结果展示。
4. 若后续部署为多实例，需要补充连接路由协调方案。
5. 微信登录与发布流程需提前准备小程序资质。

## 25. 结论

本方案采用 `微信小程序 + FastAPI 单体后端 + Windows WPF 常驻客户端` 的轻量架构，重点满足“多用户绑定同一设备、仅在线设备可发送、滚动横幅醒目展示、语音播报、开机自启常驻”的核心需求。

一期方案已足够支撑真实使用场景，并保留后续向设备组、后台管理、更多通知形态扩展的空间。该文档可直接作为后续详细设计、接口设计和实施排期的基线文档。
